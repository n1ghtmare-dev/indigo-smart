Доменный слой моей игры не знает про Three.js и Rapier. Зачем я так сделал

Игры редко пишут по чистой архитектуре. Обычно игровой объект сам держит меш, сам дёргает физическое тело и сам решает правила — так быстрее, и в геймдеве это норма.

Я в своём браузерном 3D-платформере пошёл другим путём: правила игры не знают ни про Three.js, ни про Rapier, ни про DOM. Ниже — как это устроено, во что обошлось и что дало взамен. Спойлер: главное, что дало, — тесты, которые проходят за секунды и не зависят от того, насколько медленно на этой машине рисуется кадр.

Правило, которое всё держит

Оно одно и жёсткое: в src/domain/** запрещены импорты three, rapier, DOM API и вообще любых адаптеров. Только стандартный TypeScript.

Из этого правила следует всё остальное. Домен не может «просто позвать движок» — значит, всё, что ему нужно от внешнего мира, приходит аргументом, а всё, что он хочет сделать с миром, он возвращает как данные.

Правила прогресса — чистые функции вида «событие → новое состояние + эффекты». Функция onEntityEnter не удаляет меш и не меняет коллайдер. Она возвращает новый прогресс и список эффектов, которые кто-то другой исполнит.

Порты

Между доменом и внешним миром — интерфейсы. Их немного, и весь контракт игры с физикой умещается в один экран:

export interface PhysicsPort {
  loadLevel(level: LevelDef): void;
  setMoveIntent(x: number, z: number): void;
  requestJump(): void;
  step(dt: number): void;
  getCubeState(): CubeState;
  consumeEvents(): PhysicsEvent[];
  setCubeMass(mass: number): void;
  removeEntity(index: number): void;
  spawnShedDrop(id: number, position: Vec3): void;
  removeShedDrop(id: number): void;
  applyKnockback(): void;
  respawnCube(): void;
}

export interface RenderPort {
  syncLevel(level: LevelDef): void;
  syncCube(cube: CubeState): void;
  removeEntity(index: number): void;
  syncShedDrops(drops: ReadonlyArray<ShedDropState>): void;
  render(): void;
}

Обратите внимание, чего в PhysicsPort нет. Нет RigidBody, нет Collider, нет типов Rapier вообще. Есть LevelDef, CubeState, Vec3 — мои собственные структуры. Реализация RapierPhysics знает про Rapier; всё, что выше неё, — нет.

То же самое с рендером: syncCube(cube: CubeState) — «вот состояние куба, покажи как хочешь». Адаптер на Three.js внутри творит что угодно, включая squash & stretch и пересчёт материала, — наружу это не протекает.

Цена

Врать не буду, цена есть.

Порт разрастается. Двенадцать методов в PhysicsPort — это уже не элегантный интерфейс из учебника. Каждая новая механика, которой нужно что-то от физики, добавляет метод.

Один раз пришлось продавить домен. Рендеру для squash & stretch нужна скорость куба. Скорость живёт в физике, а рендер её оттуда достать не может — он видит только CubeState. Пришлось добавить в доменную модель поле velocity, которое домену самому не нужно ни для одного правила. Это честный компромисс, а не победа архитектуры: данные поехали через центр только потому, что маршрута в обход не было.

Тюнинг живёт в одном месте. Все константы игры — в src/domain/tuning.ts, и в адаптерах нельзя писать магические числа. Дисциплина полезная, но требует привычки.

Что это дало: тесты без браузера

Правила массы, правила движения, правила прогресса и watchdog — чистые функции без зависимостей. Их можно гонять в Vitest пачками, без headless-браузера, без WASM-модуля физики, без канваса. Это быстро и, что важнее, это тесты на правила игры, а не на пиксели.

Физика тоже тестируется отдельно, а Game — с фейковой реализацией портов. Чтобы проверить, что подобранная капля увеличивает массу, не нужен Rapier: достаточно фейка, который вернёт нужное событие.

И главное: детерминированные e2e

Вот здесь чистая архитектура окупилась целиком.

Сначала о цикле. Игра крутится на фиксированном шаге с аккумулятором:

export class FixedTimestep {
  private accumulator = 0;

  constructor(
    private readonly dt: number,
    private readonly maxStepsPerFrame = 5,
  ) {}

  advance(elapsedSec: number, stepFn: () => void): void {
    this.accumulator += elapsedSec;
    let steps = 0;
    while (this.accumulator >= this.dt && steps < this.maxStepsPerFrame) {
      stepFn();
      this.accumulator -= this.dt;
      steps++;
    }
    if (steps === this.maxStepsPerFrame) this.accumulator = 0;
  }
}

maxStepsPerFrame тут не для красоты — это защита от «спирали смерти»: если кадр отрисовался медленно, накопилось много игрового времени, движок пытается догнать, из-за чего следующий кадр ещё медленнее, и так до полной остановки. Упёрлись в лимит — сбрасываем накопитель и осознанно теряем игровое время вместо того, чтобы уронить вкладку.

А теперь проблема тестов. Playwright-тест «дойди до капли и проверь, что масса выросла» в обычном виде выглядит как «нажми стрелку, подожди секунду, проверь». На быстрой машине хватает, на софтверном рендере в CI — нет, и тест мигает. Ждать по wall-clock нельзя, потому что симуляция едет со скоростью отрисовки.

Раз симуляция отделена от рендера, её можно прокрутить синхронно:

if (import.meta.env.DEV) {
  (window as unknown as Record<string, unknown>).__cubanoid = {
    getState: () => game.getCubeState(),
    getProgress: () => game.getProgress(),
    advance: (seconds: number) => {
      const step = 1 / 60;
      for (let t = 0; t < seconds; t += step) game.tick(step);
    },
  };
}

И тест перестаёт зависеть от железа:

for (let i = 0; i < 40 && c.getProgress().mass !== 5; i++) c.advance(0.1);

Это не «подожди четыре секунды», это «прокрути ровно четыре секунды игрового времени фиксированными шагами по 1/60». Результат одинаковый на моей машине и на софтверном рендере.

Хук объявлен под import.meta.env.DEV и в продакшен-сборку не попадает.

Бонус: качество рендера тоже знает про тесты

Раз уж заговорили про CI. Полный пайплайн с SSAO и bloom на софтверном GL живёт мучительно, поэтому режим качества выбирается сам:

if (requested === 'high' || requested === 'low') {
  quality = requested;
} else if (
  (typeof navigator !== 'undefined' && navigator.webdriver === true) ||
  MOBILE_UA_PATTERN.test(navigator.userAgent)
) {
  quality = 'low';
} else {
  quality = 'high';
}

navigator.webdriver === true — это и есть «нас запустил Playwright». Функциональные e2e идут на low и не тормозят; скриншот для сверки с визуальным референсом снимается отдельно с ?quality=high.

Важно, что это решение рендер-локальное: домен, физика и тюнинг про режим качества не знают ничего. Ровно так, как и задумано.

Стоило ли

Для игры на полторы минуты уровень — вопрос спорный, и я не буду утверждать, что так надо делать всем. Но три вещи я бы повторил не задумываясь:

  1. Правила игры как чистые функции. Их можно читать, тестировать и обсуждать без запуска игры.
  2. Фиксированный шаг с ограничителем. Дёшево и снимает целый класс проблем.
  3. Синхронная прокрутка симуляции для тестов. Возможна ровно потому, что симуляция не привязана к отрисовке — и именно она превратила мигающие e2e в стабильные.

В следующей части — про рендер: как обычный MeshPhysicalMaterial превращался в желе, почему transparent: true пришлось выключить и откуда на кубе брались чёрные тени.
