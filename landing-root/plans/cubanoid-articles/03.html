Куб спотыкался на идеально ровном полу. Виноваты были швы между коллайдерами

В моей браузерной игре красный желейный куб катается по каменным плитам. Плиты описаны в JSON как отдельные тайлы 1×1×1, и на старте я честно создавал для каждого тайла свой статический коллайдер в физическом движке. Пол получался идеально ровным: соседние боксы стояли встык, грань в грань, без единого зазора.

И на этом ровном полу куб спотыкался. Не всегда, не сильно — но регулярно получал микроскопический толчок вверх и терял скорость.

Эта статья — про то, что происходило на самом деле, и про алгоритм, который это вылечил. Стек: TypeScript, Rapier (WASM-порт), Three.js.

Что это было

Это классические ghost collisions на внутренних рёбрах — проблема, которая живёт во всех физдвижках, где поверхность собрана из отдельных выпуклых тел.

Механика такая. Куб у меня не идеальный параллелепипед, а roundCuboid — скруглённый бокс с радиусом скругления 0,08. Когда он скользит по одному коллайдеру и доезжает до его края, движок должен передать контакт следующему коллайдеру. Но это не один непрерывный контакт с одной плоскостью, а два независимых расчёта контакта на границе двух тел. На долю кадра куб касается одновременно края первого бокса и ребра второго — и получает импульс, которого на настоящем полу быть не должно.

Ключевое: зазора нет. Грани совпадают идеально. Проблема не в геометрии уровня, а в том, что физдвижок видит не «пол», а «много боксов, стоящих рядом».

Из этого следует и решение: убрать сами швы там, где это возможно.

Жадный мердж: 135 коллайдеров в 30

Идея простая — перед загрузкой уровня в физику слить соседние блоки одинакового сечения в один большой бокс. Строка из шести тайлов должна стать одним коллайдером длиной шесть, а не шестью коллайдерами с пятью швами внутри.

Алгоритм двухпроходный:

  1. Сливаем блоки в «полосы» вдоль оси X.
  2. Полученные полосы сливаем вдоль оси Z — так соседние ряды одинаковой формы склеиваются во всё более крупные плиты.

Условие слияния двух боксов вдоль X: совпадают Y, Z, высота и глубина, а грани по X соприкасаются — без зазора и без нахлёста:

function tryMergeAlongX(a: Box, b: Box): Box | null {
  if (!approxEq(a.cy, b.cy) || !approxEq(a.cz, b.cz)) return null;
  if (!approxEq(a.sy, b.sy) || !approxEq(a.sz, b.sz)) return null;

  const aMaxX = a.cx + a.sx / 2;
  const bMinX = b.cx - b.sx / 2;
  if (!approxEq(aMaxX, bMinX)) return null;

  const aMinX = a.cx - a.sx / 2;
  const bMaxX = b.cx + b.sx / 2;
  return {
    cx: (aMinX + bMaxX) / 2, cy: a.cy, cz: a.cz,
    sx: a.sx + b.sx, sy: a.sy, sz: a.sz,
  };
}

Здесь есть тонкость, на которой легко споткнуться: ширина sx намеренно не сравнивается. Аккумулятор жадного прохода к этому моменту уже мог вырасти шире исходного тайла — если требовать равенства ширин, полоса перестанет расти после первого же слияния.

Баг, который съел половину времени: сортировка

Первая версия жадного прохода сортировала боксы просто по координате вдоль оси слияния. Выглядит очевидно правильно. Мердж при этом почти не срабатывал: число коллайдеров после прохода почти не отличалось от числа тайлов.

Причина в том, что уровень — не одна строка. Блоки из разных рядов имеют одинаковый x и в общем порядке идут вперемешку: тайл из ряда z = -1, тайл из ряда z = 0, тайл из ряда z = 1, снова ряд z = -1… Жадный проход сравнивает соседние элементы массива — а соседями оказываются блоки из разных рядов, которые сливаться не должны и не сливаются. Аккумулятор сбрасывается на каждом шаге.

Лечится двухуровневой сортировкой: сначала группируем по всему, что должно совпадать (для оси X это cy, cz, sy, sz — то есть «сечение ряда»), и уже внутри группы сортируем по координате вдоль оси слияния:

const round = (v: number) => Math.round(v / EPS);
const groupKey = (b: Box) => [round(b.cy), round(b.cz), round(b.sy), round(b.sz)] as const;

const sorted = [...boxes].sort((a, b) => {
  const ka = groupKey(a), kb = groupKey(b);
  for (let i = 0; i < ka.length; i++) if (ka[i] !== kb[i]) return ka[i] - kb[i];
  return coord(a) - coord(b);
});

Округление ключа группы до EPS здесь не косметика. Координаты приезжают из JSON и бывают результатом деления, так что два блока одного ряда могут отличаться на 1e-16. Без округления компаратор развёл бы их по разные стороны и разорвал группу ровно там, где её рвать нельзя.

Почему EPS = 1e-4

Допуск выбран не наугад. Погрешность double на таких величинах — порядка 1e-15, то есть 1e-4 больше неё на одиннадцать порядков и уверенно ловит «почти равные» координаты. При этом минимальный осмысленный зазор между блоками в моём мире — сантиметры, то есть 1e-2 в мировых единицах: допуск на два порядка меньше и не склеит блоки, между которыми игрок должен пролезть.

Почему не мерджу по Y

Третьего прохода нет сознательно. Вертикальные швы — пол одной платформы и потолок другой — не дают skid-артефактов: чтобы поймать ghost collision, кубу надо пересекать шов движением, а не стоять на одной поверхности. Плюс в текущих уровнях блоков, совпадающих по X, Z и сечению, но разной высоты, просто не встречается. Усложнять алгоритм ради гипотетического случая не стал.

Детерминизм

Результат не зависит от порядка тайлов на входе: внутри каждого прохода боксы явно сортируются, а на выходе делается финальная сортировка по всем полям. Это не педантизм — от этого зависит воспроизводимость e2e-тестов и то, что уровень ведёт себя одинаково между запусками.

На первом уровне это даёт 135 тайлов, слитых в 30 коллайдеров. Блоки нестандартного размера или на дробных позициях ни с чем не сливаются и остаются отдельными коллайдерами. Это нормально: мердж — оптимизация против швов, а не требование к геометрии уровня.

Два соседних софтлока

Мердж убрал спотыкание, но по дороге вылезли ещё две вещи, которые я чинил в том же цикле.

Куб заклинивало в щели. Он въезжал в узкий разрыв между плитами и намертво вставал: трение о боковые стенки держало его, а горизонтальный контроль не хватало, чтобы вытолкнуть. Лечение оказалось грубым и работающим — трение самого куба выставлено в ноль:

cubeFriction: 0,

Трение поверхности при этом осталось (0.8 у плитки). Rapier комбинирует трения двух тел как среднее, так что эффективное трение стало 0.4 — куб по-прежнему не скользит как по льду, но и не заклинивается в вертикальной щели.

Watchdog на случай, если всё-таки застряли. Чистое доменное правило: если игрок жмёт кнопки, а куб за четыре секунды не сместился больше чем на 0,15 — респаун без штрафа по массе.

Важная деталь в одну строку: время копится только при активном вводе.

if (distance(pos, state.anchor) > TUNING.watchdogMinMove) {
  return { state: initialWatchdog(pos), stuck: false };
}
if (!inputActive) {
  return { state, stuck: false };
}

Без этой проверки игрок, который просто отошёл от компьютера, через четыре секунды телепортировался бы на чекпоинт. «Стою на месте» и «застрял» — разные состояния, и отличает их наличие ввода.

Итог

  • Ровный на вид пол из отдельных коллайдеров — не ровный для физического движка. Швы существуют, даже когда зазоров нет.
  • Жадный мердж соседних блоков убирает швы в направлении движения. Тридцать строк логики слияния плюс правильная сортировка.
  • Сортировка важнее самого слияния: неверный порядок обхода превращает жадный алгоритм в пустой цикл, и это не падает с ошибкой, а просто тихо не работает.
