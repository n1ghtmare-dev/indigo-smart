# Демо «Аварийный каскад» — дизайн

**Дата:** 2026-06-14
**Контекст:** дипломная защита. Комиссия открывает дашборд IndigoSmart на своих телефонах
под одним аккаунтом. Докладчик щёлкает тумблер сценария — на всех телефонах синхронно
срабатывает реакция, после чего «умный дом» автономно разрешает проблему. Все наблюдают
разрешение в реальном времени.

**Охват этой итерации:** слои 1+2 (сценарный оркестратор + фронтовый реактивный слой).
Web Push (уведомления на заблокированном телефоне) — НЕ в этой итерации, выносится отдельно.

---

## Цель и критерий успеха

Один тумблер у докладчика → за ~30 секунд на **всех** подключённых устройствах синхронно:
1. тревога (полноэкранный алерт + вибрация + звук + живой рост температуры на датчике);
2. автономная реакция дома (включение кондиционера) с видимым снижением температуры;
3. запись реальной цепочки в БД и в журнал автоматизации.

**Критерий успеха (проверяемый):** на двух браузерах одновременно открыт дашборд; запуск
сценария вызывает на обоих в пределах ~1 сек визуальную тревогу; в течение сценария в
`device_states` появляется запись о включении кондиционера, в `automation_log` — строка
о срабатывании; температура на графике сначала растёт выше порога, затем падает к норме.

## Не-цели (YAGNI)

- Web Push / service worker / VAPID — следующая итерация.
- Настоящие пороговые правила в реальном времени через 20-сек поллинг — оркестратор
  работает поверх существующего движка, не заменяя его.
- Конфигуратор сценариев в UI. Один захардкоженный сценарий «Перегрев», параметры — в коде.

## Архитектура

Три новых единицы + переиспользование существующих broadcast/`run_now`.

```
[Тумблер докладчика]
   │  POST /scenario/overheat/start
   ▼
[scenario_engine.py]  (фоновый поток, детерминированные шаги по таймеру)
   │  пишет SensorReading (рост t°), затем форсит правило (логика run_now),
   │  затем пишет SensorReading (падение t°)
   │  на каждом шаге → manager.broadcast_sync({type:"scenario_step", ...})
   ▼
[ws_manager.broadcast]  (уже существует, шлёт всем клиентам)
   ▼
[LiveEventProvider (React context)]  (новый, поднимает один WS на всё приложение)
   ├── <AlertOverlay>      — полноэкранная тревога, vibrate, звук
   ├── живой датчик t°     — гейдж/график обновляется по событиям
   └── план дома           — комната пульсирует красным → остывает
```

### Единица 1 — `scenario_engine.py` (бэкенд, новый)

Назначение: детерминированно разыграть каскад вне зависимости от 20-сек поллинга и
рандома симулятора.

- Функция `start_overheat_scenario(db_factory, actor_user_id)` запускает фоновый поток
  (`threading.Thread`, daemon) с жёстким таймлайном (значения/паузы — константы вверху файла):

  | t, сек | действие | broadcast `scenario_step` |
  |--------|----------|---------------------------|
  | 0  | старт, выбор цели (см. ниже) | `phase:"start"`, room, sensor, baseline |
  | 0..12 | впрыск `SensorReading(temperature)` 24→27→30→32 шагами по ~3 сек | `phase:"rising"`, value на каждом шаге |
  | 13 | форс правила: `DeviceState` кондиционер ON + `AutomationLog` (логика из `run_now`) | `phase:"rule_fired"`, device_id, state |
  | 14..28 | впрыск `SensorReading(temperature)` 32→28→24 шагами по ~3 сек | `phase:"cooling"`, value на каждом шаге |
  | 29 | финал | `phase:"resolved"` |

- **Выбор цели:** найти комнату, где есть и датчик температуры (`DeviceType.name="Датчик
  температуры"`), и кондиционер (`"Кондиционер"`). Если не найдено — взять первый датчик
  температуры и первый кондиционер (любой) и логировать предупреждение. ID комнаты/датчика/
  кондиционера кладутся в событие `start`, чтобы фронт знал, какую комнату подсвечивать.
- **Реакция дома:** если существует подходящее `AutomationRule` (target = кондиционер) —
  переиспользовать его (записать `last_triggered_at`, `AutomationLog`). Если правила нет —
  всё равно записать `DeviceState` ON + `AutomationLog` с понятным сообщением
  («Кондиционер включён автоматически (сценарий)»), чтобы журнал показывал цепочку.
- **Защита:** глобальный флаг «сценарий уже идёт» — повторный POST возвращает 409, чтобы
  два нажатия не накладывались. Поток сам сбрасывает флаг в `finally`.
- **Формат события** (единый для всех шагов):
  `{type:"scenario_step", scenario:"overheat", phase, room_id, room_name, sensor_device_id,
    ac_device_id, value, threshold, ts}`.

### Единица 2 — роут `routes/scenario.py` (бэкенд, новый)

- `POST /scenario/overheat/start` — `require_user_or_admin`; запускает оркестратор,
  возвращает `{ok, room_name}`; 409 если уже идёт.
- `GET /scenario/state` — `{running: bool, scenario: str|None, phase: str|None}` для
  восстановления состояния при перезагрузке вкладки.
- Регистрация роутера в `main.py` рядом с остальными.

### Единица 3 — `LiveEventProvider` + реактивные компоненты (фронт, новый)

Сейчас WS живёт только в навбаре (просто счётчик). Нужен один WS на всё приложение и
раздача событий подписчикам.

- `contexts/LiveEvents.jsx` — React-контекст: открывает один WebSocket через существующий
  хук `useWebSocket`, хранит `lastEvent`, отдаёт `subscribe(cb)` и `connected`. Провайдер
  оборачивает админ-лейаут (выше навбара и вьюх). Навбар переносит свой счётчик на этот
  контекст (один сокет вместо двух).
- `components/alert/AlertOverlay.jsx` — слушает `scenario_step`:
  - `phase:"rising"`/`"rule_fired"` → показать полноэкранный красный слой (название
    комнаты, текущая t°, иконка тревоги), запустить `navigator.vibrate([200,100,200,...])`
    (под guard — не везде поддерживается), проиграть короткий звук тревоги (Web Audio
    `AudioContext`, синтез — без бинарных ассетов, либо маленький data-URI; стартовать
    после первого user-gesture, т.к. autoplay-политика).
  - `phase:"cooling"` → сменить слой на «зелёный»: «✅ Кондиционер включён автоматически».
  - `phase:"resolved"` → плавно скрыть через пару секунд.
- **Живой датчик температуры:** компонент на дашборде/в гостиной подписывается на
  `scenario_step.value` и анимированно двигает значение/гейдж (переиспользовать
  существующий ApexCharts или простой числовой гейдж). При отсутствии активного сценария —
  обычные данные.
- **План дома** (`views/admin/floorplan/index.jsx`): комната с `room_id` из события
  пульсирует красным на `rising`, остывает к норме на `cooling`/`resolved`. Эффект только
  визуальный (CSS-класс/стиль по состоянию), без изменения CRUD-логики плана.

### Единица 4 — отдельная страница «Демо-сценарии» (фронт, новый)

- Новый пункт бокового меню «Демо-сценарии» → роут `/admin/scenarios`
  (`views/admin/scenarios/index.jsx`), зарегистрировать в `routes.js`/сайдбаре.
- На странице — карточка сценария «🔥 Перегрев»: описание, крупная кнопка «Запустить»,
  индикатор текущей фазы во время прогона (`POST /scenario/overheat/start`; кнопка
  disabled пока идёт, состояние из `GET /scenario/state`).
- Сделать расширяемой: карточки сценариев — массив конфигов, чтобы потом легко добавить
  «протечка», «охрана» без переписывания страницы.
- **Важно:** сама реакция (тревога, вибрация, живой датчик, пульсация комнаты) живёт
  глобально через `LiveEventProvider` и работает на ЛЮБОЙ открытой странице. То есть
  комиссия смотрит дашборд/план дома, а докладчик запускает сценарий со своей страницы
  `/admin/scenarios` — реакция всё равно прилетает всем.

## Поток данных (happy path)

1. Докладчик жмёт тумблер → `POST /scenario/overheat/start`.
2. `scenario_engine` поднимает поток, ставит флаг running, шлёт `scenario_step phase:start`.
3. Каждые ~3 сек: запись `SensorReading` + broadcast → все клиенты двигают датчик, на
   `rising` показывают тревогу/вибрацию/звук, комната краснеет.
4. На 13-й сек: `DeviceState` ON + `AutomationLog` + broadcast `rule_fired` → карточка
   кондиционера зелёная, журнал пополняется.
5. Фаза `cooling`: показания падают, датчик ползёт вниз, комната остывает.
6. `resolved`: оверлей плавно исчезает, флаг running снят.

## Обработка ошибок и краевые случаи

- **Повторный запуск** — 409 + тост «Сценарий уже идёт».
- **Нет цели (нет датчика/кондиционера в БД)** — фоллбэк на любые подходящие устройства;
  если совсем нет температурного датчика — 422 с понятным сообщением (на защите этого не
  будет — есть сидинг, но защищаемся).
- **Сбой потока на середине** — `try/finally` снимает running-флаг; клиент по
  `GET /scenario/state` восстановит, что сценарий не идёт; оверлей имеет авто-таймаут
  скрытия, чтобы не «залипнуть» на экране.
- **`navigator.vibrate` / звук недоступны** (iOS Safari, нет user-gesture) — деградируем
  тихо: визуальная часть работает всегда; вибрация/звук — best-effort под guard.
- **Поздно подключившийся клиент** — пропустит начало; это допустимо для демо. `GET
  /scenario/state` даёт лишь факт running, без перемотки.
- **Переподключение WS** — хук уже умеет reconnect; контекст переподписывается.

## Тестирование

- **Бэкенд (pytest, есть `tests/`):**
  - `start_overheat_scenario` создаёт ожидаемую последовательность `SensorReading`
    (рост затем падение) и ровно одну запись `DeviceState` ON + одну `AutomationLog`
    (поток можно прогнать синхронно/с замоканными паузами).
  - повторный старт при running → 409.
  - выбор цели: комната с датчиком и кондиционером выбрана корректно; фоллбэк работает.
- **Фронтенд:** smoke — `LiveEventProvider` раздаёт событие подписчику; `AlertOverlay`
  показывается на `rising` и скрывается на `resolved` (vibrate/звук замоканы).
- **Ручная проверка перед защитой:** два браузера, запуск сценария, синхронная реакция,
  записи в БД и журнале (это и есть критерий успеха выше).

## Декомпозиция работ

1. Бэкенд: `scenario_engine.py` + `routes/scenario.py` + регистрация + pytest. *(ядро,
   самостоятельно тестируется без фронта)*
2. Фронт: `LiveEventProvider` + перевод навбара на него.
3. Фронт: `AlertOverlay` (визуал + вибрация + звук).
4. Фронт: живой датчик температуры + пульсация комнаты на плане.
5. Фронт: отдельная страница «Демо-сценарии» с картой запуска (расширяемая).
6. Интеграционная ручная проверка по критерию успеха.

Слои строятся снизу вверх: после шага 1 каскад уже реален в БД/журнале и виден через WS;
шаги 2–5 наращивают видимый «вау».
